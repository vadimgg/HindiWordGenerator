# 06 · UI

## 1. Diagnosis

The current UI feels inconsistent because there is **no shared design language** —
each page invented its own type scale, buttons, spacing, and prose. Symptoms:
too much always-on text (the Audio page narrates itself with a description, a CLI
chip, a `BACKEND · --BACKEND` label, a status line, and a redundant "X IS READY"
card); competing button styles; everything shown at once (Deliver stacks package
export + AnkiConnect setup + deck config + presets + toggles + data health);
pipeline framing leaking everywhere.

## 2. Principles

1. **The UI is a helper, never the only path.** Every screen maps to CLI commands
   (doc 05); an agent or human can do the same in a terminal.
2. **The UI mirrors the files.** Reorder → `library.db`; settings → `config.toml`;
   import → merges into the library. No UI-only state.
3. **Reference material gets a home, surfaced contextually** — we do not delete
   the Anki instructions or the CLI command, we organize them (§5).
4. **One component vocabulary**, applied by a shared shell so pages can't drift.

## 3. One shell for every page (DaVinci-style)

Every page reuses the same frame; only the canvas + inspector content change.

```
┌────────────────────────────────────────────────────────────────────────────┐
│ ✦ Complete Hindi   Generate Import Organize Words Audio Anki Package  ⌘ ? ⚙   │
├──────────────────────────────────────────────────────┬───────────────────────┤
│   CANVAS  (the sentence / word list or audio timeline) │   INSPECTOR           │
│                                                        │  (selection / context)│
├──────────────────────────────────────────────────────┴───────────────────────┤
│   [ primary action ]                              context actions              │
└────────────────────────────────────────────────────────────────────────────┘
```

- Top bar: deck name · page switcher · the persistent `⌘ ? ⚙` cluster.
- Canvas: the work surface (a list/timeline of sentences or words).
- Inspector: details for the current selection, or page settings.
- Action bar: exactly one primary action; contextual actions on the right.

## 4. Design tokens (intentionally tiny)

| Token | Rule |
|---|---|
| Type | 3 sizes: page title, row text, caption. No scattered ALL-CAPS. |
| Buttons | 3 roles only: primary (one per screen, amber), secondary (outline), ghost (text). |
| Color | amber = the single primary action; teal = neutral interactive; slate = everything else. |
| Status | a dot, not a sentence: ● ready · ○ missing · ◐ stale. |
| Density | DaVinci-dense but grouped; whitespace via grouping, not paragraphs. |

These live as CSS variables + a few primitives: `Page`, `Toolbar`, `List`, `Row`,
`Inspector`, `Button`, `StatusDot`, `Dropdown`.

## 5. Three consistent homes for secondary info

Nothing useful is deleted — each kind of secondary content has one home, in the
same place on every page, surfaced contextually.

**⚙ Settings** — persistent config (writes `config.toml`, doc 05 §7): Deck
(collection title, language), Display (lead, show secondary), Audio (default
backend, ElevenLabs key, default voice), Anki (deck/subdeck names, presets,
replace behavior), Package (default destination). API keys and deck config move
out of the working pages into Settings.

**? Help** — the instructions you don't want to lose: Connect Anki (AnkiConnect
add-on, permissions, config block), Set up ElevenLabs, How the pipeline works.

**⌘ CLI** — a single reveal per page showing the command for the current
view/action.

**Contextual surfacing**: inline notes appear only when actionable and deep-link
into a home — e.g. `AnkiConnect ● offline — How to connect?` → Help; `○ no
ElevenLabs key — Add in Settings` → Settings › Audio.

Because Settings/Help/CLI are shell primitives, every page mounts them the same
way and registers its own topic + command — consistency by construction.

## 6. Pages

| Page | Canvas | Primary action | Inspector |
|---|---|---|---|
| Generate | raw input + draft list | Extract → / Enrich → | run/packet, transport choice |
| Import | source picker + preview | Import → | provenance, conflicts |
| Organize | sentence list, drag-reorder, sections | — (autosaves) | selected sentence fields (+ locks) |
| Words | lexicon list (word · #sentences · meanings) | — | word detail, its sentences |
| Audio | sentence list w/ audio status + play | Generate missing | voice/backend, per-row regen |
| Anki | selection summary | Send to Anki | deck target (defaults from Settings) |
| Package | selection summary | Export package | destination, filter, json/db |

## 7. Build order

1. Shell + tokens + the `⌘ ? ⚙` primitives (Settings drawer, Help drawer, CLI
   reveal) — this is the design system.
2. Convert **Audio** as the reference page (key/backend defaults → Settings,
   instructions → Help).
3. Split **Deliver** into **Anki** + **Package** with the same pattern.
4. Roll the primitives across Organize and Words.

Studio's *backend* edges (transport, handlers, DTO mapping, route split) are
covered in [02](./02-crate-and-module-design.md) and [09](./09-reuse-and-patterns.md);
this document covers the *UX*. Consistency is automatic because every page draws
from the same primitives.
